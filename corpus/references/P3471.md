# P3471 — Standard library hardening

## Problem
Wide swathes of the C++ standard library trade safety for performance:
`std::vector::operator[]` does not bounds-check; `std::optional::value()`
does (it throws), but `std::optional::operator*()` does not; the iterator
arithmetic in `<ranges>` is full of preconditions that are UB on
violation. Every major implementation (libc++, libstdc++, MSVC STL) has
its own *hardening mode* that opts into runtime checks for these
preconditions — `_LIBCPP_HARDENING_MODE`, `_GLIBCXX_DEBUG`,
`_ITERATOR_DEBUG_LEVEL`. They are incompatible with each other and
their build-time configuration is brittle.

P3471 standardises *which* operations are hardened, *how* the
hardening is configured (build-time mode + runtime handler), and what
happens on violation (contract-violation handling, integrated with
[[P2900]]).

## Key syntax

- Library-wide hardening levels:
  - `fast` — current behaviour (no checks; UB on violation).
  - `harden` — required checks enabled; violations call the
    hardening handler.
  - `harden_with_deadlock_detection` — full debug mode (slower,
    catches more).
- Build-time selection via implementation-defined macro
  (`__STDCPP_HARDENING_MODE`).
- Hardening violations route through the contract-violation
  handler from [[P2900]] — same observation/enforcement semantics.

## Canonical example

```cpp
#include <vector>
#include <print>

void show(const std::vector<int>& v, std::size_t i) {
    // Under harden: out-of-range access calls the contract handler
    // and (by default) terminates with a diagnostic.
    // Under fast: undefined behaviour (matches pre-C++26 release builds).
    std::print("{}\n", v[i]);
}
```

## Canonical example: handler installation

```cpp
void install_logging_hardening_handler() {
    std::contracts::set_contract_violation_handler(
        [](const std::contracts::contract_violation& v) {
            if (v.kind() == std::contracts::contract_kind::hardening) {
                log::record(v.comment(), v.location());
                // observe semantic → continue
            }
            // … other contract kinds handled elsewhere
        });
}
```

## Pre-C++26 equivalent

```cpp
// libc++ specific:
//   -D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_EXTENSIVE
// libstdc++ specific:
//   -D_GLIBCXX_DEBUG
// MSVC STL:
//   _ITERATOR_DEBUG_LEVEL=2
```

Each is implementation-specific. None compose across libraries. Code
that needs portable hardening had to ship its own checked wrappers
(`gsl::span`, `absl::CheckedVector`, …).

## Gotchas

- Hardening is *off* by default in release builds for backwards
  compatibility. You must opt into `harden` at build time; the
  default remains "fast" so existing binaries don't slow down on
  recompile.
- Violations go through the contract-violation handler. If you
  globally install a handler for [[P2900]] contracts, you handle
  hardening violations too — inspect `contract_kind` to differentiate.
- Hardening checks may *add* preconditions over time as the
  implementation discovers more checkable cases. Code that assumed
  "out-of-range subscript is UB, so let it through" may start
  faulting at the contract handler in a later patch release.
- Mixed-mode binaries (one TU built `fast`, another `harden`) work
  but lose the guarantee for any object that crosses TU
  boundaries — keep the mode consistent across the binary.
