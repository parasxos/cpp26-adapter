# P2795 — Erroneous behaviour for uninitialized reads

## Problem
Reading an uninitialized variable of automatic-storage scalar type
was *undefined behaviour* under prior standards. UB lets the compiler
assume the read never happens, license optimisations that delete
surrounding code, and produce results that vary per build and per
platform — the "uninitialized read" bug class is one of the largest
real-world C++ security CVE drivers.

C++26 introduces a third behavioural category: **erroneous behaviour
(EB)**. An uninitialized scalar read is now *erroneous*: the value is
required to be a *defined erroneous value* (zero for most
implementations) and the implementation is *required* to diagnose
the read (compile-time when provable, runtime via a sanitiser or
trap otherwise).

## Key syntax

- Default: every scalar local now reads as if zero-initialised; reading
  before assignment is *erroneous*, not undefined.
- `[[indeterminate]]` attribute: opt back into the old indeterminate
  behaviour for a specific variable when you genuinely want the
  uninitialised performance (e.g., the read is preceded by an
  unconditional write that the compiler can't see through).

```cpp
int x;                          // erroneous-on-read; effective value 0
int y [[indeterminate]];        // indeterminate (legacy); UB on read
```

## Canonical example

```cpp
int compute(int* buf, int n) {
    int total;                  // erroneous-on-read; reads as 0 if not set
    for (int i = 0; i < n; ++i) {
        total += buf[i];
    }
    return total;               // safe (reads zero if buf was empty)
}
```

## Canonical example: opt out for performance

```cpp
int read_packet(int fd) {
    // Buffer fully overwritten by ::read; opting into indeterminate
    // saves a 1 KiB zero-fill on every call.
    char buf[1024] [[indeterminate]];
    auto n = ::read(fd, buf, sizeof(buf));
    return parse(buf, n);
}
```

## Pre-C++26 equivalent

```cpp
int compute(int* buf, int n) {
    int total = 0;                  // explicit zero-init (every time)
    for (int i = 0; i < n; ++i) {
        total += buf[i];
    }
    return total;
}
```

The pre-C++26 form requires programmer discipline (every author of
every function must remember). EB inverts the default: zero-init is
free, opt out only when measured-meaningful.

## Gotchas

- "Erroneous" is *not* "undefined". The compiler may not assume the
  read never happens — it has a specific (defined) value, the
  implementation just isn't required to make it useful.
- The defined erroneous value is implementation-defined. Most
  implementations choose zero, but portable code should still
  treat it as "almost certainly a bug".
- `[[indeterminate]]` reintroduces UB. Use it sparingly and with
  a comment explaining why the variable is guaranteed-overwritten
  before any read.
- Aggregate types follow the rule member-by-member: an aggregate
  containing one `[[indeterminate]]` member is partially erroneous.
