# P3068 — Allowing exception throwing in constant evaluation

## Problem
Constexpr-evaluated code in C++23 and earlier could not `throw`. This
broke a category of compile-time idioms that *would* be expressible
otherwise:

- `std::optional::value()` calling `throw bad_optional_access{}` is
  not constexpr.
- `std::stoi("not a number")` cannot be constexpr because it would
  throw `invalid_argument`.
- Reflection ([[P2996]]) signals errors (e.g., "no such member") via
  exceptions; without P3068, every diagnosable reflection error would
  collapse the entire constant evaluation.

P3068 allows `throw`, `try`, and `catch` to participate in constant
evaluation. An uncaught exception during constexpr evaluation is a
*constant evaluation error* (the surrounding `constexpr` context
fails to be a constant expression, with a diagnostic identifying the
exception).

## Key syntax

No new syntax — existing `throw` / `try` / `catch` become permitted
in constexpr contexts.

```cpp
constexpr int parse(std::string_view s) {
    try {
        int n = 0;
        for (char c : s) {
            if (c < '0' || c > '9') throw std::invalid_argument{"not a number"};
            n = n * 10 + (c - '0');
        }
        return n;
    } catch (const std::invalid_argument&) {
        return -1;
    }
}

static_assert(parse("42")    == 42);
static_assert(parse("oops")  == -1);
```

## Canonical example: reflection error handling

```cpp
#include <meta>

template <typename T>
constexpr std::size_t field_index(std::string_view name) {
    auto members = std::meta::nonstatic_data_members_of(^^T);
    for (std::size_t i = 0; const auto& m : members) {
        if (std::meta::identifier_of(m) == name) return i;
        ++i;
    }
    throw std::out_of_range{"no such field"};   // surfaces at compile time
}

struct Point { int x, y; };
static_assert(field_index<Point>("y") == 1);
// static_assert(field_index<Point>("z"));      // compile error: no such field
```

## Pre-C++26 equivalent

Return `std::expected<T, E>`, sentinels, or `std::optional`:

```cpp
constexpr std::expected<int, std::string_view> parse_v1(std::string_view s) {
    int n = 0;
    for (char c : s) {
        if (c < '0' || c > '9') return std::unexpected{"not a number"};
        n = n * 10 + (c - '0');
    }
    return n;
}
```

The pre-C++26 form forces an explicit-error return type on every
constexpr API. Library code that wants both a runtime-throwing form
and a compile-time form had to keep two code paths in sync.

## Gotchas

- Throwing during *manifestly constant evaluation* (e.g., inside a
  `static_assert`) becomes a hard compile error. This is usually
  what you want — but be deliberate about catching internally if
  the operation has a meaningful "no, but continue" semantic.
- Exception types themselves must be constexpr-constructible. Most
  `<stdexcept>` types are; user-defined exception types may need
  `constexpr` constructors added.
- The diagnostic the compiler emits for an uncaught constexpr
  exception is implementation-defined; mine usually echoes
  `e.what()` if it's a string literal stored constexpr-friendly.
