# P2300 — `std::execution` (senders/receivers)

## Problem
Pre-C++26 C++ has three incompatible models for concurrent and
asynchronous work:

- `std::async` / `std::future` — heap-allocated continuations, no
  cancellation, no scheduling primitives, eager start.
- `std::thread` + `std::mutex` — too low-level for most application code.
- Library coroutines — composable but lock you into an awaitable type
  and require executor plumbing per library.

`std::execution` introduces a uniform *algebra* for asynchronous work:

- **Senders** describe *lazily-built* asynchronous work that will
  complete with a value, an error, or stopped.
- **Schedulers** specify *where* work runs (thread pool, GPU stream, …).
- **Receivers** consume completion signals (value/error/stopped) from
  a sender.

Senders compose via pipeable algorithms (`then`, `let_value`,
`when_all`, …) and only execute when started against a receiver,
which gives lazy, allocation-free pipelines that work across every
async backend that implements the sender concept.

## Key syntax

- `std::execution::just(v…)` — sender that immediately completes with `v…`.
- `sender | std::execution::then(fn)` — apply `fn` to the value.
- `sender | std::execution::upon_error(fn)` — handle the error
  completion channel.
- `std::execution::when_all(s1, s2, …)` — concurrent fan-out, join on all.
- `std::execution::let_value(sender, [](auto v) → sender { … })` — async
  bind (the "monadic" combinator).
- `std::execution::start_detached(sender)` — fire-and-forget.
- `std::execution::sync_wait(sender)` — block the current thread until
  the sender completes; returns `std::optional<std::tuple<…>>`.
- `std::execution::schedule(sched)` — sender that completes on `sched`.

## Canonical example

```cpp
#include <execution>
#include <print>

namespace ex = std::execution;

int main() {
    auto pool      = ex::static_thread_pool(4);
    auto scheduler = pool.get_scheduler();

    auto pipeline =
          ex::schedule(scheduler)
        | ex::then([] { return 7; })
        | ex::then([](int x) { return x * 6; })
        | ex::then([](int x) { std::print("{}\n", x); return x; });

    auto [result] = ex::sync_wait(pipeline).value();   // prints 42, returns 42
}
```

## Canonical example: concurrent fan-out

```cpp
auto fetch_a = ex::schedule(sched) | ex::then([] { return get_a(); });
auto fetch_b = ex::schedule(sched) | ex::then([] { return get_b(); });

auto combined =
      ex::when_all(fetch_a, fetch_b)
    | ex::then([](A a, B b) { return merge(a, b); });

auto [out] = ex::sync_wait(combined).value();
```

## Pre-C++26 equivalent

```cpp
#include <future>

int main() {
    auto fa = std::async(std::launch::async, [] { return get_a(); });
    auto fb = std::async(std::launch::async, [] { return get_b(); });
    auto out = merge(fa.get(), fb.get());   // sequential await, not when_all
}
```

The pre-C++26 form: (1) silently allocates a heap state for each
`std::async`; (2) has no notion of scheduler, so you can't pin work to
a specific pool; (3) `.get()` blocks rather than chaining; (4) errors
propagate via exceptions only — no `stopped` channel for cooperative
cancellation.

## Gotchas

- Senders are *lazy*. A sender that is built but never connected to a
  receiver never runs — the work is silently discarded. If you forget
  the final `sync_wait` / `start_detached`, the pipeline is dead.
- `sync_wait` blocks the current thread. Calling it from the scheduler
  the sender targets will *deadlock*. Use `start_detached` for
  fire-and-forget, or join against a different scheduler.
- The `stopped` channel is for *cooperative* cancellation. A sender
  has to thread a stop token through its work; long-running C work
  inside `then` won't stop just because a token was signalled.
- Custom senders must implement the `connect`/`get_env`/`set_value`/
  `set_error`/`set_stopped` machinery correctly. Most users only ever
  *consume* senders; if you're authoring one, follow the wording
  closely — concepts are strict.
- Real-world scheduler implementations are mostly third-party today
  (NVIDIA's `nvexec`, Bloomberg's `unifex`-derived port, …). The
  in-tree `std::execution` ships *adapters* and the algorithm
  algebra; you bring the scheduler.
