# P1306 — Expansion statements (`template for`)

## Problem
Compile-time iteration over a *heterogeneous* sequence — a `std::tuple`,
a parameter pack, or a constexpr range of reflections — required either
recursive function templates, `std::apply` + index sequences, or
`if constexpr` ladders. None compose: iterating *and* knowing the
compile-time index *and* having access to the type at each step needed
all three techniques layered together.

`template for` is a *language* statement that loops over such a
sequence at compile time, instantiating the body separately for each
element. It unblocks the obvious idiomatic form of "for each
non-static data member of T, do X" — the canonical use case for
[[P2996]] reflection.

## Key syntax

```
template for (init-statement-or-binding : expandable-sequence)
    statement
```

The expandable sequence may be:

- a parameter pack expression
- a `std::tuple`-like object (anything `get<I>`-able)
- a constexpr range — usually a `std::define_static_array(…)` over a
  reflection sequence
- an `std::integer_sequence`

Each iteration of the loop is a *distinct instantiation* of the body
with its own scope. The loop variable is `constexpr` in compile-time
contexts.

## Canonical example: sum a tuple

```cpp
#include <tuple>

template <typename... Ts>
constexpr auto tuple_sum(const std::tuple<Ts...>& t) {
    using common = std::common_type_t<Ts...>;
    common acc{};
    template for (const auto& x : t) {
        acc += x;
    }
    return acc;
}

static_assert(tuple_sum(std::tuple{1, 2.0, 3.0f}) == 6.0);
```

## Canonical example: iterate reflected members

```cpp
#include <meta>

template <typename T>
constexpr int member_count(const T&) {
    int n = 0;
    template for (constexpr auto m :
                  std::define_static_array(
                      std::meta::nonstatic_data_members_of(^^T))) {
        ++n;
    }
    return n;
}

struct Point { int x; int y; int z; };
static_assert(member_count(Point{}) == 3);
```

## Canonical example: parameter pack

```cpp
template <typename... Ts>
void print_all(Ts&&... args) {
    template for (auto&& a : {args...}) {
        std::print("{}\n", a);
    }
}
```

## Pre-C++26 equivalent

```cpp
// 1. recursive variadic templates
template <typename Tup, size_t I = 0>
constexpr auto tuple_sum_v1(const Tup& t) {
    if constexpr (I == std::tuple_size_v<Tup>) return 0;
    else return std::get<I>(t) + tuple_sum_v1<Tup, I + 1>(t);
}

// 2. std::apply + fold expression
template <typename Tup>
constexpr auto tuple_sum_v2(const Tup& t) {
    return std::apply([](const auto&... xs) { return (xs + ...); }, t);
}

// 3. std::index_sequence + comma-fold
template <typename Tup, size_t... Is>
constexpr auto tuple_sum_v3(const Tup& t, std::index_sequence<Is...>) {
    auto acc = decltype(std::get<0>(t)){};
    ((acc += std::get<Is>(t)), ...);
    return acc;
}
```

Each pre-C++26 form trades obvious-iteration for some template
machinery. None of them give the loop variable a name in scope —
which is exactly what reflection-driven loops want.

## Gotchas

- The loop body is *instantiated separately* per element. If the body
  contains a substantial amount of code, compile-time and code-size
  cost scale linearly with the sequence length.
- The loop variable's *type* may differ per iteration when iterating a
  tuple — `auto&&` is the right binding most of the time.
- Inside the body, `continue` and `break` work, but they apply only
  to the current iteration's instantiation. Jumping out of an
  expansion statement does *not* short-circuit subsequent iterations
  in the way runtime `break` would in a `for` loop.
- Be careful with non-`constexpr` `static` locals inside the body —
  each instantiation declares its own.
