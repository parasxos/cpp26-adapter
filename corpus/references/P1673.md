# P1673 — `std::linalg`

## Problem
Numerical C++ code that needed BLAS-style linear algebra (matrix
multiply, dot product, AXPY, triangular solve, …) had to depend on a
non-standard library: Eigen, Armadillo, MKL, OpenBLAS, …  These vary in
API conventions (column-major vs row-major, in-place vs out-of-place,
batched-vs-not). `std::linalg` standardises the BLAS-1/2/3 operations
on top of `std::mdspan` ([[P0009]]).

The headline value is *not* maximum performance — vendor BLAS will
usually win — but *portable correctness*: code that calls
`std::linalg::matrix_product(A, B, C)` compiles everywhere and
delegates to whatever optimised path the standard library has.

## Key syntax

All algorithms live in `<linalg>` and take `std::mdspan` views. Free
functions are pipe-friendly. Tag types select layout (general,
triangular, hermitian, …).

- `std::linalg::dot(x, y)` — dot product.
- `std::linalg::scaled(α, x)` — scaling adapter (no copy).
- `std::linalg::add(x, y, z)` — z = x + y.
- `std::linalg::matrix_product(A, B, C)` — C = A·B.
- `std::linalg::matrix_vector_product(A, x, y)` — y = A·x.
- `std::linalg::triangular_matrix_left_product(...)` — TRMM family.

## Canonical example: GEMM

```cpp
#include <linalg>
#include <mdspan>
#include <vector>

void multiply_3x3(const float* a, const float* b, float* c) {
    auto A = std::mdspan<const float, std::extents<int, 3, 3>>(a);
    auto B = std::mdspan<const float, std::extents<int, 3, 3>>(b);
    auto C = std::mdspan<      float, std::extents<int, 3, 3>>(c);
    std::linalg::matrix_product(A, B, C);
}
```

## Canonical example: AXPY (y ← α·x + y)

```cpp
void axpy(float alpha, std::mdspan<const float, std::dextents<int, 1>> x,
                       std::mdspan<      float, std::dextents<int, 1>> y) {
    std::linalg::add(std::linalg::scaled(alpha, x), y, y);
}
```

## Pre-C++26 equivalent

```cpp
// Pick one:
//   - Eigen:        Map<Matrix3f>(c).noalias() = Map<Matrix3f>(a) * Map<Matrix3f>(b);
//   - vendor BLAS:  cblas_sgemm(CblasRowMajor, ..., a, ..., b, ..., c, ...);
//   - Hand-rolled:  triply nested for-loop (slow, no SIMD without effort)
```

Each path is a non-standard dependency that has to be vendored, linked,
or written. `std::linalg` accepts whichever the implementation chooses
under the hood.

## Gotchas

- `std::linalg` is *value-oriented*: most algorithms take output mdspans
  as parameters rather than returning. The output mdspan's extents
  must match the algorithm's contract; mismatches are UB (or, with
  hardening from [[P3471]], an erroneous behaviour).
- Element types are templated. Built-in floating-point types are
  always supported; user-defined types must model the appropriate
  algebraic concepts (`std::linalg::matrix_field` etc.).
- The `scaled` and `conjugated` adapters return *views*, not copies —
  modifying the underlying mdspan during the algorithm is UB.
- Performance varies dramatically by implementation. For a
  performance-critical inner loop, profile against vendor BLAS;
  for the 90% case (one-shot solves, glue code), `std::linalg` is
  enough.
