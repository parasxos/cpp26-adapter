# P2545 — Read-copy-update (RCU)

## Problem
RCU is the read-side-cheaper counterpart to hazard pointers ([[P2530]]).
Where hazard pointers cost one atomic publish per protected pointer,
RCU costs *zero* atomics on the read side — readers simply enter a
*read-side critical section* and dereference. Writers update by
publishing a new version and *waiting for a grace period* (until every
reader has exited the section it was in at update time) before
freeing the old version.

The trade-off is push-vs-pull: hazard pointers push protection per
read, RCU defers reclamation until "nobody is reading anything from
this domain". RCU shines for read-mostly, latency-sensitive workloads;
hazard pointers shine for high write-rate workloads with bounded
protection lifetimes.

C++26 standardises RCU as `std::rcu_*` and aligns the API with
existing Linux-kernel and userspace-RCU practice.

## Key syntax

- `std::rcu_obj_base<T>` — CRTP base for RCU-managed objects;
  provides `retire(deleter = …)`.
- `std::rcu_default_domain()` — get the process-default RCU domain.
- `std::synchronize_rcu()` — block until every reader currently in
  a read-side critical section exits. Use sparingly; prefer
  `retire()` for asynchronous reclamation.
- Read-side critical sections are denoted by *RAII guards* in the
  C++26 form (no explicit `rcu_read_lock`/`unlock` in normal use).

## Canonical example: read-mostly map

```cpp
#include <rcu>
#include <atomic>

struct Snapshot : std::rcu_obj_base<Snapshot> {
    std::vector<int> data;
};

std::atomic<Snapshot*> current{ new Snapshot{} };

int read_size() {
    auto guard = std::rcu_default_domain().get_reader();  // RAII
    Snapshot* s = current.load(std::memory_order_acquire);
    return static_cast<int>(s->data.size());              // safe: guard pins s
}

void replace(std::vector<int> new_data) {
    auto* fresh = new Snapshot{ std::move(new_data) };
    auto* old   = current.exchange(fresh, std::memory_order_release);
    old->retire();                  // freed once no reader holds it
}
```

## Canonical example: synchronous reclamation

```cpp
void shutdown() {
    delete current.exchange(nullptr);
    std::synchronize_rcu();        // wait for any in-flight readers
    // … now safe to tear down the RCU domain entirely
}
```

## Pre-C++26 equivalent

Use `liburcu` or fold the equivalent into your own infra. Linux kernel
code has had RCU forever; userspace got it via Mathieu Desnoyers'
`liburcu`. P2545 is essentially "userspace-RCU, in the IS".

```c
/* userspace-rcu */
rcu_read_lock();
struct snapshot* s = rcu_dereference(current);
int n = s->size;
rcu_read_unlock();
```

## Gotchas

- Read-side critical sections must be *short* and *non-blocking*. A
  thread inside a read-side critical section that goes to sleep
  extends the grace period, blocking reclamation for every writer
  in the domain.
- `synchronize_rcu` is a *fence over readers*, not a barrier between
  writers. Writers still need their own ordering to ensure their
  publish happens before they call retire.
- Mixing RCU domains is allowed but tricky. Most applications use
  the default domain; a domain split is a deliberate isolation
  choice (e.g., one domain per subsystem with different latency
  budgets).
- RCU is *not* a replacement for hazard pointers. Use RCU for
  read-mostly snapshots, hazard pointers for high-throughput
  read-write graphs.
